# OpenRow v1 product and engineering specification

Status: proposed for approval. This document is the implementation handoff for the next thread.

## 1. Product contract

**Outcome:** A fast, local, open-source macOS 26+ menu-bar utility that lets a keyboard user reveal targets with `Hyper–J`, type a home-row hint to move the pointer and click, or enter Scroll mode and use H/J/K/L without switching focus to OpenRow.

**Allowed implementation:** One native macOS app, its unit/integration tests, local fixtures, open-source documentation, signing/notarization automation, and direct-download packaging.

**Protected behavior:** The frontmost app stays frontmost; hint activation visibly repositions the pointer before mouse-down/up; only OpenRow's active shortcut/mode keys are suppressed; Escape always cancels; permission refusal never blocks Settings; no captured key stream, accessibility content, or usage telemetry leaves the device.

**Proof:** Focused unit tests, an instrumented fixture app, direct browser observation on macOS 26, a fresh-install permission pass, and a manual compatibility matrix covering Finder, Safari, Chrome, System Settings, Xcode, multiple displays, alternative keyboard layouts, and accessibility appearances.

**Stop when:** Every P0 acceptance criterion passes on the latest signed build on macOS 26; macOS 27-specific checks are either passed on a test machine/VM or explicitly listed as pending rather than inferred.

## 2. Product definition

### Primary user and job

A keyboard-first Mac user wants to keep both hands on the home row while moving between text entry and ordinary graphical controls. The frequent job is: reveal a target, identify its short hint, type it, and continue working without a focus switch or trip to the trackpad.

The product personality is calm, exact, fast, and native. It is a utility, not a command-center dashboard. The overlay must feel instantaneous and visually unambiguous; the Settings app should disappear into macOS conventions.

### v1 modes

1. **Click mode — P0.** `Hyper–J` scans the frontmost app's visible accessibility tree, draws unique home-row hints beneath valid clickable elements on every display, narrows hints as keys arrive, moves the pointer to the chosen target, and sends left mouse-down/up.
2. **Scroll mode — P0.** `Hyper–K` identifies visible scroll regions, outlines the active one in blue, and consumes H/J/K/L until Escape or the toggle shortcut exits. Shift makes the current motion a faster dash. Tab and Shift-Tab change the active scroll region.
3. **Menu-bar control — P0.** The menu shows Enabled/Paused state, Click mode, Scroll mode, Settings, a concise permission state, and Quit. Commands show their current shortcut.
4. **Ignored apps — P1.** A bundle-ID list disables activation in selected apps without changing global defaults.
5. **Feedback — P1.** Optional system sound for click, cancel, and unavailable state. Sound is never the only feedback.

### Defaults

| Setting | Default | Reason |
| --- | --- | --- |
| Click mode | `Hyper–J` | Explicit user workflow; J is a home-row anchor. |
| Scroll mode | `Hyper–K` | Adjacent but distinct home-row anchor. |
| Hint alphabet | physical A S D F G H J K L positions | Nine easy keys; fixed-length codes provide 81 two-key targets and 729 three-key targets. |
| Click action | left click at visible-frame center | Matches the requested pointer-and-click behavior. |
| Scroll keys | H J K L | Familiar Vim geometry. |
| Scroll dash | Shift + direction, 3× base delta | Clear, reversible speed increase. |
| Scroll speed | 18 px per repeat tick, tunable | Conservative starting point to validate on hardware. |
| Theme | system appearance | Avoids duplicating macOS appearance settings. |
| Launch at login | on after successful onboarding opt-in | Utility is useful when continuously available; the user remains in control. |
| Sound | off | Quiet default; visible state remains sufficient. |
| Data/telemetry | none | Local assistive behavior does not need an account or network. |

“Hyper” means Control + Option + Shift + Command generated by the user's existing Caps Lock remapper. Native Caps Lock dual-role remapping is not part of v1 because it materially expands low-level keyboard behavior and conflict risk.

### Explicit non-goals for v1

- OCR, screen capture, image recognition, a coordinate grid, or clicking pixels that have no accessibility metadata.
- Drag and drop, text selection, middle click, arbitrary gestures, or macros.
- Search-by-label text, tutor mode, chain clicking, Mission Control, or menu navigation.
- iOS, iPadOS, Windows, or Linux.
- Accounts, sync, analytics, update service, paid licensing, or a Mac App Store build.
- Reusing HomeRow assets, source, product copy, iconography, name, or private behavior.

Search mode and chain clicking are deliberately P2 candidates. They should be added only after the label-only loop is fast and reliable.

## 3. Interaction model

### Global state machine

```text
Disabled / permission-limited
             │ capability becomes ready
             ▼
           Idle ── Hyper–J ──► Collecting click targets
             │                       │ success
             │                       ▼
             │                  Click hints visible ── valid label ──► Click ──► Idle
             │                       │ Escape / toggle / app change / tap failure
             │                       └────────────────────────────────────────► Idle
             │
             └── Hyper–K ─────► Collecting scroll areas ──► Scroll mode ── Escape/toggle ──► Idle
```

Only one mode exists at a time. Starting one mode cancels the other. A frontmost-app change, display reconfiguration, secure input/unavailable event tap, or permission loss cancels the current mode and passes future input through.

### Click-mode sequence

1. The event tap recognizes the configured activation chord and suppresses only that chord.
2. The mode controller snapshots the frontmost PID and visible display configuration.
3. The AX scanner traverses the frontmost application's visible windows on a cancellable background task. It collects elements with a finite visible frame and a click semantic (`AXPress` support or an allow-listed clickable role/subrole).
4. The classifier removes hidden, disabled, offscreen, zero-area, duplicate, overlay-owned, ignored-app, and unsafe elements. It keeps a diagnostic reason count without retaining UI text.
5. Targets sort deterministically by display, vertical position, horizontal position, role priority, then AX traversal order.
6. The label assigner uses the current input source's characters for configured physical home-row positions. It chooses one fixed code length for the current target count, so no full label is a prefix of another.
7. An `NSPanel` per display draws labels below a target when space permits, otherwise above or inside its edge. Collision resolution nudges labels within a bounded radius without changing the target point.
8. Each typed label character filters the set. Nonmatching hints disappear immediately; Backspace restores one step; Escape/toggle cancels.
9. On a unique complete label, the overlay becomes click-through, the pointer moves to the clamped center of the current visible target frame, and Quartz posts move, mouse-down, and mouse-up events in order.
10. All overlay panels close, captured state is discarded, and unrecognized future keys pass through.

If the accessibility tree changes after collection, validate the target's PID, enabled state, frame, and onscreen intersection immediately before clicking. If invalid, cancel with a short visual warning and never click stale coordinates.

### Scroll-mode sequence

1. Activation snapshots the frontmost app and collects visible scroll areas, preferring the nearest scrollable ancestor of the accessibility-focused element, then the region beneath the pointer, then largest visible area.
2. A blue outline and numbered badge identify the active region. Other candidates get quiet numbered badges only when there is more than one.
3. Key-down/repeat for H/J/K/L produces pixel scroll events located at the active area's safe center. Key-up stops immediately. Shift uses the dash delta. Opposing held directions cancel on that axis.
4. Tab/Shift-Tab cycles regions; digits 1–9 select a visible numbered region; Escape/toggle exits.
5. The overlay never accepts pointer events or activates OpenRow. If the area disappears or the frontmost app changes, exit instead of scrolling an uncertain target.

### Shortcut editing and discoverability

All global bindings are editable at any time in Settings > Shortcuts. Each row uses a native-looking shortcut recorder with these behaviors:

- Activating the field enters “Press a shortcut” state; Escape cancels and Delete clears.
- Modifier-only and Hyper chords are representable, but the two P0 mode bindings must remain distinct.
- The stored value is physical key code + modifier flags. The displayed primary character is regenerated when the current input source changes.
- A local conflict prevents Save; a common macOS shortcut conflict produces a warning, not a false claim that every third-party conflict can be detected.
- Applying a valid edit replaces the event-tap match table atomically with no restart.
- Modifier glyphs are accompanied by an accessibility value such as “Control–Option–Shift–Command–J.”
- Current bindings appear in the OpenRow menu beside their commands. Standard Command-Comma remains Settings and Command-Q remains Quit.

This is the planned interpretation of “macOS discovery text/discoverability”: shortcuts are exposed through native menus, visible recorder values, help text during recording, and VoiceOver-readable plain language rather than being hidden knowledge.

## 4. Native architecture

### Technology decision

- **Language/toolchain:** Swift 6 mode with Xcode 26.6.
- **Deployment target:** macOS 26.0; compile on 26 first, then add a macOS 27 CI/test lane when the stable SDK is available.
- **UI:** SwiftUI for the Settings scene and menu content; AppKit for `NSApplicationDelegate`, nonactivating overlay panels, window levels, screen/Space behavior, and event integration.
- **System APIs:** ApplicationServices/Accessibility (`AXUIElement`), CoreGraphics (`CGEventTap`, mouse and scroll events), Carbon Text Input Sources for physical-key display translation where required, ServiceManagement (`SMAppService`), OSLog/signposts.
- **Persistence:** typed preference keys backed by `UserDefaults`; bundle IDs for ignored apps; no database.
- **Dependencies:** none at runtime for v1. Use native code for shortcut recording to keep global-event semantics and input-source handling under test.
- **Distribution:** Developer ID Application signing, Hardened Runtime, notarized DMG or ZIP, no App Sandbox initially.

### Module boundaries

```text
OpenRow app shell
├── App
│   ├── lifecycle, Settings scene, menu-bar item
│   └── dependency composition
├── Domain
│   ├── ModeController state machine
│   ├── Target, HintCode, Shortcut, ScrollRegion
│   └── HintAssigner and filtering rules
├── Accessibility
│   ├── PermissionClient
│   ├── AXTreeWalker (bounded, cancellable)
│   ├── ClickTargetClassifier
│   └── ScrollRegionFinder
├── Input
│   ├── EventTap lifecycle and fail-open policy
│   ├── ShortcutMatcher / recorder
│   └── InputSourceTranslator
├── Overlay
│   ├── OverlayCoordinator (one panel per display)
│   ├── ClickHintsView
│   └── ScrollRegionsView
├── Actions
│   ├── PointerController / ClickExecutor
│   └── ScrollEngine
├── Settings
│   ├── General, Shortcuts, Clicking, Scrolling, Ignored Apps, About
│   └── permission and unavailable states
└── Infrastructure
    ├── PreferencesStore, LaunchAtLogin
    ├── FrontmostApplicationMonitor
    └── Diagnostics (local, privacy-preserving counters only)
```

The domain layer owns state and deterministic rules without importing AppKit or AX. System adapters are protocols so unit tests use immutable AX snapshots and synthetic key events. All AX calls live behind one actor or serial executor; AppKit window mutation remains on `MainActor`; the event-tap callback does constant-time classification and hands work to owned queues.

### Invariants

- Event input is pass-through by default.
- Overlay panels never become main windows and ignore mouse events.
- A target belongs to the frontmost PID captured for the active mode.
- A click is sent only after revalidation and coordinate conversion.
- Hint codes are unique for one snapshot and generated from configured physical key positions.
- Mode state has a single owner; cancellation is idempotent.
- Changing Settings cannot partially mutate active input matching.
- No raw key events, AX strings, window titles, or bundle usage history are persisted or logged.

## 5. Permissions and first run

The first launch opens a small setup window instead of triggering system permission prompts immediately.

1. **Welcome:** one sentence explaining the click and scroll outcome, with Continue and Quit.
2. **Accessibility:** explains “Find controls and click the one you choose.” A Grant Access button calls the trusted-client prompt and offers Open System Settings. The row polls only while visible/active.
3. **Input Monitoring:** explains “Recognize your shortcuts while another app is active.” Request via the CoreGraphics API; offer the exact System Settings destination if needed.
4. **Try it:** a local fixture with three real buttons lets the user invoke Click mode and demonstrates hints without leaving OpenRow.
5. **Ready:** optional Launch at Login checkbox, current shortcuts, Finish.

The user can close setup, deny either permission, or revisit it from the menu. In a limited state, the menu and Settings work, mode commands are disabled with the missing capability named, and no recurring alert appears.

## 6. Acceptance criteria

### P0 — must pass before v1

| ID | Observable acceptance |
| --- | --- |
| P0-01 | On a clean macOS 26 installation, OpenRow explains each required permission before prompting; denial leaves menu and Settings usable; granting permissions updates status without reinstalling. |
| P0-02 | With another app frontmost, pressing configured Click mode leaves that app frontmost and renders hints over every supported, visible clickable target on all active displays. |
| P0-03 | For 1–729 targets, every visible hint is unique, uses only configured physical positions, has fixed length for that snapshot, and typing a prefix hides nonmatches without leaking the characters into the target app. |
| P0-04 | Completing a hint revalidates the target, visibly moves the pointer to its onscreen frame, posts one left mouse-down/up pair, closes overlays, and performs the intended action exactly once. |
| P0-05 | Escape or the active toggle exits either mode; app switch, display reconfiguration, permission loss, event-tap disable, and stale target also exit safely with future keyboard input passing through. |
| P0-06 | Scroll mode outlines the chosen region without focus change; H/J/K/L scroll left/down/up/right; Shift increases delta; releasing the key stops; Tab and Shift-Tab select regions; Escape exits. |
| P0-07 | Click and Scroll shortcuts can be recorded, cleared, and changed while the app runs; a Hyper chord records correctly; duplicate OpenRow bindings are rejected; menus and VoiceOver values update immediately. |
| P0-08 | U.S. and Dvorak physical-key tests select the intended hints, and one Japanese IME test proves label entry does not depend on committed text events. |
| P0-09 | Overlay frames and click/scroll points remain correct with Retina scaling, a secondary display left of the primary (negative origin), menu-bar relocation, display disconnect, and separate Spaces. |
| P0-10 | Settings is operable with Full Keyboard Access and VoiceOver; labels survive system text enlargement; Reduce Transparency, Increase Contrast, Reduce Motion, and light/dark appearance retain hierarchy and state. |
| P0-11 | For a warm accessibility snapshot of 100 targets on the test Mac, activation-to-first-paint is measured with signposts and meets p50 ≤ 150 ms and p95 ≤ 300 ms over 30 runs; no run exceeds 750 ms without an unavailable/progress state. |
| P0-12 | Static review and a network-denied runtime check confirm no telemetry/account/network dependency and no raw key, UI text, or window-title persistence. |

### P1 — complete before a public 1.0 release if time permits

- Ignored apps can be added with `NSOpenPanel`, show icon/name/bundle ID, and be removed keyboard-only.
- Launch at Login uses `SMAppService` and reports denied/system-managed states.
- Optional sounds follow system output and volume; every sound has simultaneous visual feedback.
- A Diagnostics view exposes capability state, event-tap state, target counts, timing percentiles, and last error category without private UI content.
- Signed/notarized artifact passes Gatekeeper on a clean macOS 26 VM.

## 7. Test strategy

### Test-first seams

Write tests before implementation for these pure seams:

1. `HintAssigner`: count thresholds, uniqueness, allowed alphabet, stable ordering, filtering/backspace.
2. `ShortcutMatcher`: modifier normalization, Hyper, repeats, toggles, conflicts, layout changes.
3. `ModeReducer`: every transition and fail-open cancellation.
4. `ClickTargetClassifier`: roles/actions, hidden/disabled/offscreen/duplicate decisions.
5. `CoordinateMapper`: AX top-left global coordinates to AppKit/CoreGraphics display geometry.
6. `ScrollEngine`: directions, opposing keys, repeat timing, dash delta, stop-on-key-up.

### Integration fixture

Build one local `OpenRowFixture` app containing buttons, links, icon-only controls, disabled and hidden elements, nested groups, two independent scroll views, a WebKit view, an editable field, a menu, popover, sheet, custom accessibility elements, rapidly changing layout, and a deliberate unsupported canvas. It is both an automated integration target and the onboarding Try It surface.

### Manual compatibility matrix

| Context | Core proof |
| --- | --- |
| Finder | toolbar, sidebar, list rows, context changes |
| Safari | page links/buttons, toolbar, nested scrolling |
| Chrome | page and browser chrome; bounded traversal and latency |
| System Settings | native controls, sheets, permission return |
| Xcode | dense native tree and editor scrolling |
| Mission Control/full screen | v1 must fail safely; full support remains deferred unless the spike proves it cheaply |
| Two displays/Spaces | overlay ownership, scaling, negative origins, hot-plug |
| U.S., Dvorak, Japanese IME | physical shortcut and hint behavior |
| VoiceOver/FKA/contrast settings | Settings semantics and visual adaptation |

Use a fresh VM or separate signed bundle identity for TCC flows. A day-to-day machine with cached permission history is not valid first-run proof.

## 8. Delivery slices for the build thread

These are local implementation slices, not tracker tickets. Ticket publication requires a separate explicit request.

### Slice 0 — signed feasibility tracer

Create the smallest signed macOS app that can request/check both permissions, install a fail-open event tap, enumerate and outline one target in Finder/Safari, move and click it, identify one scroll region, and send one scroll event. Prove on macOS 26 before building polished Settings. Stop and revise architecture if cross-app behavior or TCC cannot be made reliable.

### Slice 1 — deterministic core and fixture

Add domain types, mode reducer, hint assignment, shortcut normalization, coordinate mapping, and the fixture app. Tests must be green before wiring system adapters.

### Slice 2 — click-mode vertical slice

Connect AX scanning → classification → hint overlay → typed filter → revalidated pointer click. Add cancellation, signposts, multi-display panels, and Safari/Finder/Chrome evidence.

### Slice 3 — scroll-mode vertical slice

Connect scroll-area discovery → selection overlay → repeat-aware H/J/K/L scroll events. Add dash, region traversal, cancellation, and nested-scroll fixtures.

### Slice 4 — native shell and settings

Build menu-bar lifecycle, permission setup, General/Shortcuts/Clicking/Scrolling panes, shortcut recorder, ignored-app model, launch at login, and local diagnostics. Settings must use standard controls and system Liquid Glass.

### Slice 5 — hardening and release candidate

Run the compatibility/accessibility matrix, fix valid failures, measure latency, test clean permissions, add privacy/security documentation, choose and add the approved open-source license, sign/notarize, and produce a reproducible release artifact.

Each slice ends only when its visible behavior and focused checks pass. A compile, unit-test pass, or local unsigned build is evidence for its own claim, not for the whole app.

## 9. Decisions for approval

The recommended default is:

- Native Quiet design direction in `DESIGN.md`.
- Swift 6 + SwiftUI/AppKit hybrid, direct Developer ID distribution, macOS 26.0 floor.
- Label-only Click mode and H/J/K/L Scroll mode as P0; Search and chain clicks after v1.
- MIT license for low-friction community adoption.

If accepted, the next thread can begin at Slice 0 without more product discovery. A different license does not block the feasibility slice, but it must be chosen before any public source release.
